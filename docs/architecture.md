# Архитектура расширения 1С: Редактор конфигураций

## Назначение

VSCode-расширение `v8vscedit` предоставляет два независимых блока:

1. **[Навигатор метаданных](./metadata-navigator.md)** — дерево объектов конфигураций и расширений из XML-выгрузки.
2. **[Языковая поддержка BSL](./bsl-language-support.md)** — LSP-клиент для внешнего `bsl-analyzer`.

Дополнительно — независимая webview-панель **[«Изменения метаданных»](./git-metadata-changes.md)**
(`v8vsceditChanges`): `git status` рабочей копии в терминах объектов метаданных, с полноценными
git-операциями (stage/unstage/discard/commit/diff); дерево панели повторяет навигаторную иерархию
основного дерева конфигурации (обрезанную по изменениям), переиспользуя и Vue-компонент отрисовки,
и саму структуру `MetadataTreeProvider`.

Внутри той же панели — второй сворачиваемый блок **[«История»](./git-history-graph.md)**: граф
git-коммитов всего репозитория (свёрнут по умолчанию, грузится лениво при первом раскрытии), где выбор
коммита раскрывает inline изменённые объекты метаданных того же коммита — read-only потребитель движка
панели изменений (`aggregateMetadataChanges`, `changesDtoBuilder`, `changesTreeAssembler`), с собственным
чистым ядром раскладки графа по дорожкам (`infra/git/GitLogReader`, `GitLogParser`, `GitGraphLayout`) и
тонким чистым helper'ом состояния (`ui/views/changes/changesHistorySection.ts`), которым владеет тот же
`MetadataChangesViewProvider` — отдельного webview-провайдера/вкладки/команды для истории нет.

### Декомпозиция God-классов на тонкий фасад + подмодули

Правило зафиксировано в `CLAUDE.md` (раздел «Инвариант изменений» → «Декомпозиция
God-класса», запрет №17): большой класс дробится на тонкий фасад/барель + набор
файлов-подмодулей по ответственности **в подпапке того же слоя**, публичный API и
поведение не меняются байт-в-байт. Для XML-генераторов обязателен предварительный
байт-golden-тест как входное условие рефакторинга.

Реализованные образцы паттерна:

- `ui/mcp/V8McpServer.ts` (фасад, только HTTP-транспорт/сессии/Host-Origin-защита)
  + `ui/mcp/registration/*` — регистрация MCP-инструментов по доменам
  (`McpNavigationTools`, `McpConfigInfoTools`, `McpTemplateTools`,
  `McpExternalObjectTools`, `McpFormTools`, `McpSubsystemTools`, `McpRoleTools`,
  `McpConfigLifecycleTools`, `McpPropertyTools`) + `McpMutationGate` (общий
  post-mutation шлюз и формат-хелперы ответов) + `McpRegistrationDeps` (контракт
  зависимостей, разделяемых всеми доменными модулями).
- `infra/xml/MetadataXmlCreator.ts` (фасад) + `infra/xml/creator/*`
  (`creatorShared`, `rootObjectBuilders`, `auxiliaryFileBuilders`,
  `childElementBuilders`) — построение корневых XML-объектов, вспомогательных
  файлов и дочерних элементов метаданных.
- `infra/xml/ExternalObjectService.ts` (фасад) + `infra/xml/external/*`
  (`externalObjectShared`, `externalObjectXml`, `bspRegistration`,
  `externalObjectFiles`, `externalObjectValidation`) — работа с EPF/ERF.
- `infra/xml/DataCompositionSchemaService.ts` (фасад) + `infra/xml/dcs/*`
  (`dcsShared`, `schemaParse`, `schemaBuilders`, `editOperations`) — СКД.
- `infra/xml/form/FormBuilders.ts` (реэкспорт-барель) + `infra/xml/form/builders/*`
  (`formBuilderShared`, `formElements`, `formAttributes`, `formCommands`,
  `formDocument`) — построение XML управляемых форм.

  (порядок ключей свойств корневых объектов; `FORM_PROPERTY_SECTION` — контракт
  с webview) + `propertyExtractors.ts` (XML-экстракторы и форматтеры значений).
  Состав свойств выбора форм по виду — `FORM_PROPERTY_KEYS_BY_KIND` в
  `infra/xml/PropertySchema.ts`, см.
  [metadata-navigator.md](./metadata-navigator.md#панель-свойств-где-живёт-порядок-ключей-и-секция-формы).

  (резолвер блокировки редактирования) + `propertyNodeClassification.ts`
  (классификация и snapshot узлов).
- `infra/xml/TypedFieldPropertyRules.ts` (фасад, 708 → 240 строк) +
  `infra/xml/typedField/TypedFieldOwnerRules.ts` (ДАННЫЕ — двумерная таблица
  правил владелец×роль) + `infra/xml/typedField/PropertyBlockEditor.ts`
  (МЕХАНИКА — точечная splice-правка блоков `<Properties>` без знания самих

Во всех случаях `switch` по `MetaKind`/виду объекта, где он был, оставлен как есть
(это диспетчер поведения, а не реестр данных) — декомпозиция не подменяла его
таблицей, это отдельная задача при появлении настоящего дублирования данных.

### Паттерн: чтение данных из базы через пакетный Конфигуратор (file-handoff)

Когда UI-команде нужны данные, которых нет в XML-выгрузке, а есть только в самой
базе 1С (пример — список расширений, уже подключённых к базе, для команды
`v8vscedit.connectExtension`), связка устроена в три слоя:

1. **CLI-команда** (`cli/commands/<name>.ts`, образец — `listDbExtensions.ts`)
   запускает пакетный Конфигуратор с нужным ключом (`/DumpDBCfgList
   -AllExtensions`) и `/Out <tmp>`, затем **только при успешном завершении
   (`exitCode === 0`)** переносит результат во входной `-ResultFile`, который
   передаёт вызывающая сторона. Гейт разбора — **код возврата процесса, а не
   содержимое лога**: при ошибке (платформа старее той, что понимает флаг;
   недоступная база) `-ResultFile` не создаётся, и вызывающая сторона узнаёт о
   сбое по его отсутствию, не пытаясь угадывать причину по тексту вывода.
2. **Чистый парсер** в `infra/` (образец — `infra/environment/ExtensionListParser.ts`)
   без `vscode`/spawn: снимает BOM (байтовый UTF-8/UTF-16LE/UTF-16BE через
   `iconv-lite` + символьный `U+FEFF`, оставшийся после декодирования),
   разбирает строки, при необходимости считает чистую функцию выбора для UI
   (`planExtensionChoices`). Все ветки покрываются 100% здесь, а не в
   оркестраторах.
3. **UI-обёртка** (`ui/commands/.../*CommandRunner.ts`, образец —
   `ExtensionCommandRunner.listConnectedDatabaseExtensions`) спавнит CLI через
   `runInternalCliCommand`, читает `-ResultFile` тем же чистым парсером и
   возвращает `undefined` при любом сбое (нет `env.json`, CLI завершился с
   ошибкой, старая платформа без нужного флага). Ручного fallback-ввода нет:
   при `undefined` вызывающий диалог прекращает операцию явным сообщением
   об ошибке, а не переключается на ручной ввод значения пользователем.

Почему `-ResultFile`, а не marker-блок в stdout: `LineBufferedDecoder`
(`infra/process/OutputDecoder.ts`) буферизует и перекодирует вывод процесса
построчно (OEM-866/Win1251) — это годится для логов, но рискует испортить
произвольные данные внутри маркера при таком роундтрипе. Канал через `/Out
<файл>` уже устоявшийся — его использует каждая из `export-configuration`/
`import-configuration`/`update-configuration`/`repository-*`.

Образец целиком: `v8vscedit.connectExtension` — список расширений для QuickPick
берётся через `list-db-extensions` (CLI) → `listConnectedDatabaseExtensions`
(UI-обёртка) → `resolveExtensionNameToConnect` (сам диалог, только выбор из
базы, без пункта «Ввести вручную…» и без `showInputBox`):
- `undefined` от UI-обёртки (нет подключения к базе/`env.json`, платформа
  старее 8.3.11 — флаг `-AllExtensions` не поддерживается) →
  `showErrorMessage` с точной причиной и подсказкой минимальной версии
  платформы, операция прекращается;
- в базе нет расширений → `showInformationMessage('В подключённой базе нет
  расширений.')`, операция прекращается;
- все расширения базы уже подключены (`planExtensionChoices(...).allConnected`)
  → `showInformationMessage('Все расширения базы уже подключены.')`, операция
  прекращается;
- иначе — `showQuickPick(plan.selectable, …)` только по вычисленному
  `planExtensionChoices` списку неподключённых расширений базы.

Функций `promptExtensionNameManually`/`validateExtensionName` и типа
`ExtensionPickItem` в коде больше нет — подключение расширения возможно
только выбором из списка базы.

### Паттерн: бинарный обмен CF/CFE через пакетный Конфигуратор (`/DumpCfg`/`/LoadCfg`)

Выгрузка/загрузка конфигурации и расширений в бинарные файлы `.cf`/`.cfe` (в
отличие от паттерна file-handoff выше) не читает данные из базы для UI, а
**меняет** содержимое — либо создаёт файл на диске, либо необратимо заменяет
конфигурацию в базе. Связка: `infra/cfFile/` (чистые данные и guard'ы, без
`vscode`/spawn) → `cli/commands/dumpCfFile.ts`/`loadCfFile.ts` (команды
`dump-cf`/`load-cf`, алиасы `db-dump-cf`/`db-load-cf` — совпадают с именами
существующих 1С-скилов) → `ui/commands/ext/CfFileCommandRunner.ts` (тонкая
обёртка спавна, переиспользует `resolveConnectionFromSettings`/
`runInternalCliCommand` из `ExtensionCommandRunner`, как импорт/обновление) →
`ui/commands/ext/CfFileCommands.ts` (диалоги QuickPick/SaveDialog/OpenDialog) и
`ui/mcp/registration/McpConfigLifecycleTools.ts` (`v8vscedit_dump_cf`/
`v8vscedit_load_cf`) — оба вызывают ровно один и тот же `CfFileCommandRunner`.

**Всё поведение платформы ниже снято эмпирически** прогонами на реальном
Конфигураторе 8.3.27.1989 на временных файловых базах (`1cv8 CREATEINFOBASE
"File=<каталог>;"` создаёт базу за секунды, полный круг проверки — минуты;
удобный источник отличающейся конфигурации для сравнения — свой же
`ConfigurationScaffoldService`), а не выведено из документации платформы:

- **`-AllExtensions` у `/DumpCfg`/`/LoadCfg` использовать нельзя.** С каталогом
  в качестве пути — exit 1 «Is a directory»; с файлом — **exit 0, «Сохранение
  конфигурации успешно завершено», и результат байт-в-байт равен обычной
  выгрузке ОСНОВНОЙ конфигурации**, то есть флаг молча делает не то, что от
  него ожидают. Причина глубже одного флага: заведомо не существующий ключ
  `-ЗаведомоНетТакого` тоже даёт exit 0 — **пакетный Конфигуратор вообще не
  диагностирует неизвестные ключи**. Следствие для всего проекта: `exitCode`
  подтверждает только «Конфигуратор не упал на том, что понял», а не
  «выполнено именно то, что просили». Поэтому у `buildCfFileDesignerArgs`
  (`infra/cfFile/CfFileArgs.ts`) нет параметра, из которого мог бы получиться
  `-AllExtensions`, а единственная реальная защита самого вектора аргументов —
  точный регресс-тест (`cfFileArgs.test.ts`), а не проверка кода возврата.
  Сценарий «все расширения» делается циклом по `/DumpDBCfgList -AllExtensions`
  (см. `list-db-extensions` выше), а не этим флагом — реализация в подразделе
  «Пакетный случай» ниже.
- **`/LoadCfg` не обновляет конфигурацию базы данных.** Замер: после загрузки
  основная конфигурация — 75408 байт, конфигурация БД осталась 4973; значения
  совпали только после отдельного `/UpdateDBCfg`. Отсюда — отдельный шаг
  применения (`applyToDatabase` в MCP, вопрос-предложение в UI после загрузки)
  и формулировка сообщения об успехе, которая явно говорит, что база ещё не
  обновлена.
- **Ненулевой код возврата не означает отсутствия побочных эффектов.**
  Неудачная `/LoadCfg -Extension <новое имя>` всё равно регистрирует
  расширение в базе; неудачная `/DumpCfg` всё равно оставляет на диске
  16-байтный файл-мусор. Отсюда — staging-схема выгрузки ниже и запрет на
  формулировки вида «ничего не изменилось» в текстах ошибок.
- **Тестовая установка платформы 8.5.1 идёт без Конфигуратора** (только
  `1cv8c`/`1cv8s`) — проверка поведения на 8.5 не проводилась и заявлять её
  нельзя.

**Staging-схема выгрузки** (`dumpCfFile.ts`): `/DumpCfg` пишет во временный
файл `resolveDumpStagingPath` в ТОМ ЖЕ каталоге, что и целевой (перенос —
атомарное переименование внутри одной ФС), и переносится на целевой путь
только при `exitCode === 0`; staging удаляется в `finally` независимо от
исхода. Проверено вживую: при сбое целевой файл не появляется, а уже
существующий файл не портится. Имя staging-файла оканчивается маркером
`DUMP_STAGING_SUFFIX` (`.v8vscedit.part`), по которому опознаётся остаток
прерванной выгрузки (см. «Пакетный случай» ниже); перенос и уборка —
`moveStagingToTarget`/`safeRemoveFile` из `cli/core/onecCommon.ts`.

**Общий замок операций** (`ui/commands/ext/configurationOperationLock.ts`) —
вынесен из `ExtensionCommands.ts`, где модульный флаг `isUpdatingConfigurations`
был развёрнут вручную трижды. Замок общий (module-level singleton) сознательно:
импорт из базы, обновление базы и выгрузка/загрузка CF-файла работают с одной и
той же базой и выгрузкой, поэтому конкурентный запуск любой пары из них
повредил бы данные. `v8vscedit_dump_cf`/`v8vscedit_load_cf` берут тот же замок
через `withConfigurationOperationLock` в `McpConfigLifecycleTools.ts` — MCP-агент
и пользователь работают с одной базой, и разделять замок по источнику вызова
нельзя.

**Осознанное отклонение от единого post-mutation пути.** После успешной
`/LoadCfg` НЕ вызываются ни `suppressConfigurationReloadForFiles`/
`markChangedConfigurationByFiles`, ни `markConfigurationsClean`, ни инвалидация
hash-кэша — файлы XML-выгрузки проекта при загрузке CF физически не меняются,
поэтому пометить их «изменёнными» или «чистыми» было бы ложью в любую сторону.
Конкретно: если бы конфигурацию пометили «изменённой относительно базы»,
команда «обновить изменённые конфигурации» залила бы СТАРЫЕ файлы проекта
обратно в базу поверх только что загруженного CF, обнулив результат операции.
Вместо этого пользователю после загрузки явно показывается предупреждение,
что XML-выгрузка проекта больше не соответствует базе, и предлагается импорт
конфигураций (`v8vscedit.importConfigurations`); MCP возвращает то же самое
через поле `projectSourcesOutdated: true`. **Это правило намеренно нарушает
общий пункт «Единый post-mutation путь» из раздела про MCP-сервер ниже** — при
похожих задачах не «чинить» это обратно без повторного замера платформы.

#### Пакетный случай: все расширения базы одной операцией (`dump-cfe-all`/`load-cfe-all`)

Выгрузка/загрузка ВСЕХ расширений базы построена на тех же примитивах, что
одиночный обмен выше. Связка слоёв:

- `infra/cfFile/` — чистые решения без `vscode`/spawn: `CfeBatchNaming`
  (санитизация имени расширения в имя `.cfe`, `~N` при коллизиях внутри плана,
  `planCfeDumpFiles`), `CfeBatchManifest` (`cfe-dump.json`), `CfeBatchPlan`
  (`validateCfeDumpDirectory`, `planCfeLoad` — предполётные отказы),
  `CfeBatchReport` (машинный отчёт CLI ↔ обёртка);
- `cli/commands/dumpCfeAll.ts`/`loadCfeAll.ts` (алиасы `db-dump-cfe-all`/
  `db-load-cfe-all`) + общий `cfeBatchShared.ts`; отчёт возвращается через
  `-ResultFile` (тот же file-handoff, что у `list-db-extensions`);
- `ui/commands/ext/CfeBatchCommandRunner.ts` (спавн CLI, разбор отчёта) →
  `CfeBatchCommands.ts` (диалоги; команды `v8vscedit.dumpAllExtensionsToCfe`/
  `v8vscedit.loadAllExtensionsFromCfe`) и пункты в `getNodeActions` на узле
  `extensions-root` (пакетные операции работают со ВСЕЙ базой — место им на
  контейнере расширений, не на корне конфигурации и не на одном расширении);
- MCP `v8vscedit_dump_all_cfe`/`v8vscedit_load_all_cfe`
  (`McpConfigLifecycleTools.ts`) зовут тот же `CfeBatchCommandRunner` под тем
  же `configurationOperationLock`.

Решения, которые нельзя «починить» обратно:

1. **Механизм — цикл по именам из `/DumpDBCfgList -AllExtensions`, а не флаг.**
   У `/DumpCfg`/`/LoadCfg` ключа `-AllExtensions` нет (см. эмпирику выше): он
   принимается молча и операция идёт над ОСНОВНОЙ конфигурацией, агент получает
   рапорт об успехе и файл не с теми данными. Ключа `-NamesFile` в реализации
   нет; список расширений всегда берётся из базы. Флаг `AllExtensions` на входе
   обеих CLI-команд отвергается guard'ом `assertNoAllExtensionsFlag` до
   `resolveConnection`.
2. **Вектор аргументов — под точной поэлементной сверкой**
   (`cfeBatchCliRun.test.ts`, вектор КАЖДОЙ итерации), включая встречное
   утверждение «`-AllExtensions` есть ровно у `/DumpDBCfgList` и ни у кого
   больше»; `/DumpCfg` — только `-Extension <имя>` и staging рядом с целью,
   `/LoadCfg` — только путь `.cfe` и `-Extension <имя>`, `/UpdateDBCfg` не
   запускается вовсе. Это единственная защита: по `exitCode` и логу ошибку в
   аргументах не видно.
3. **Асимметрия политик отказа.** Dump ПРОДОЛЖАЕТ после сбоя одного расширения:
   базу он не трогает, 14 корректных бэкапов из 15 ценны, каждый стоит минут
   работы платформы. Load ОСТАНАВЛИВАЕТСЯ на первом отказе: остальные получают
   `notAttempted`, сбойный попадает в отдельную категорию `failedAt` со
   `stateUncertain: true` (неудачная `/LoadCfg` нового расширения всё равно
   регистрирует его в базе — «не загружено» утверждать нельзя), а продолжать
   заливку поверх неопределённого состояния нельзя. Все отказы, которые можно
   вычислить заранее (расширение есть в каталоге, но нет в базе без
   `createMissing`; манифест ссылается на отсутствующий файл), отбиваются ДО
   первого `/LoadCfg` и останавливают всё, включая здоровые расширения.
   MCP-контракт зеркально разный: `v8vscedit_dump_all_cfe` при частичном отказе —
   УСПЕХ со списком `failed`; `v8vscedit_load_all_cfe` при `failedAt` —
   исключение (база в промежуточном состоянии, штатным итогом это не является).
4. **Маркер принадлежности staging-файла — `DUMP_STAGING_SUFFIX =
   '.v8vscedit.part'`** (`infra/cfFile/CfFileValidation.ts`, рядом с
   `resolveDumpStagingPath`); правило общее для одиночной и пакетной выгрузки.
   Своим остаток признаёт `isDumpStagingFileName` ТОЛЬКО по маркеру, а не по
   форме уникального суффикса: форм две (`pid-время` у одиночной, `pid-время-
   индекс` у пакетной), правило по форме одну из них не узнавало вовсе, а
   пользовательский файл `.backup.2024-01-15.part` под него подходил и
   удалялся бы молча.
5. **Уборка staging-остатков — в начале прогона** (`removeStagingLeftovers` в
   `dumpCfeAll.ts`), а не увеличением таймаута завершения. Обрыв процесса
   (SIGKILL при отмене из UI через 5 с после SIGTERM, падение, отключение
   питания) `finally` не выполняет; щедрый grace лишь сдвигает границу, за
   которую выгрузка большого расширения всё равно выйдет.
6. **Манифест `cfe-dump.json` описывает ТОЛЬКО текущий прогон, и это
   сознательно.** Санитизация имени необратима (`A:B` и `A/B` → `A_B.cfe`),
   поэтому «файл → имя расширения» хранится в манифесте. Сливать в него записи
   прошлого прогона нельзя: это поставило бы подпись «результат этой выгрузки»
   на файлы, которых она не создавала — смешение поколений с видом
   легитимности. Вместо этого загрузка возвращает `restoredByFileName` — имена
   файлов, расширение для которых восстановлено по имени файла, а не по
   манифесту (каталог собран вручную или содержит остатки прерванной
   выгрузки); сигнал идёт в CLI-журнал, в уведомление UI и агенту через MCP.
   Файлы, помеченные в манифесте `failed`, и пустые `.cfe` в план загрузки не
   берутся (прежний одноимённый файл старше остальных бэкапов набора).
7. **Общая механика staging** — `moveStagingToTarget`/`safeRemoveFile` в
   `cli/core/onecCommon.ts` рядом с `createTempDir`/`safeRemoveDir`; её
   используют и `dump-cf`, и `dump-cfe-all`. Второй копии temp+rename быть не
   должно.
8. **Post-mutation путь для load не вызывается** — то же сознательное
   отклонение и с тем же обоснованием, что у одиночного `v8vscedit_load_cf`
   (см. выше). `applyToDatabase` делает `/UpdateDBCfg -Extension <имя>` по
   одному на каждое ЗАГРУЖЕННОЕ расширение строго после последнего `/LoadCfg`
   (`/UpdateDBCfg -AllExtensions` применил бы и не загружавшиеся расширения);
   вектор применения живёт в `update-configuration`, `load-cfe-all` его не
   дублирует. Ответ инструмента содержит `projectSourcesOutdated: true`.

**О числе покрытия.** «100%» у `ui/commands/ext/CfeBatchCommands.ts` — это 100%
от ~78 неигнорированных строк из 273: под `c8 ignore` оставлено только то, что
требует пользователя и платформы (диалоги, спавн CLI); цикл проверяется на
POSIX-заглушке Конфигуратора (`cfeBatchCliRun.test.ts`). Читать число как «файл
проверен целиком» нельзя.

Раскладка проекта (`src/cf`, `src/cfe/<имя>`) переехала из `cli/core/
projectLayout.ts` в `infra/fs/ProjectLayout.ts` — она нужна и CLI (для
резолвинга файла настроек подключения), и UI (`CfFileTarget.buildCfApplyTarget`
строит цель `/UpdateDBCfg` после загрузки CF); `cli/core/projectLayout.ts`
остался тонким re-export, чтобы не появилось второго источника знания о
раскладке (запрет №2 CLAUDE.md).

Два новых MCP-инструмента и канон их аргументов — в
[mcp-paths.md](./mcp-paths.md#62-инструменты-обмена-cfcfe-через-пакетный-конфигуратор).

### Атомарная запись файлов выгрузки (`infra/fs/AtomicFileWriter.ts`)

Любая запись файла выгрузки (и служебных кэшей) идёт подменой, а не прямым `fs.writeFileSync`:
обрыв прямой записи на середине оставляет обрезанный XML, а битый XML одного объекта делает
нечитаемой ВСЮ конфигурацию, а не один объект. Модуль даёт две функции:

- `resolveAtomicTempPath(target, uniqueSuffix)` — чистая (ФС не трогает): путь временного файла;
- `writeFileAtomic(target, data)` — запись во временный файл рядом с целью и `rename` поверх неё.

Свойства, которые важно не потерять при правках:

- **Временный путь не оканчивается на `.xml`.** Имя — `.<имя цели>.<pid>.<время>.<счётчик>.tmp`.
  Watcher `src/**/*.xml` (`Container.wireFileWatcher`) иначе видел бы временный `.xml` и поднимал лишний
  reload дерева на каждую запись метаданных. Суффикс ставится ПОСЛЕ исходного расширения.
- **Тот же каталог, что у цели** — `rename` атомарен только в пределах одного тома.
- **Симлинк.** Если цель — символическая ссылка, подменяется файл, на который она указывает, а не сама
  ссылка (иначе выгрузка, подключённая симлинком, молча «отвалилась» бы от источника после первой правки).
- **Права существующего файла переносятся** на временный: `rename` подменяет inode, и без `chmod` файл
  получал бы режим по умолчанию.
- **Отказ громкий.** При любой ошибке временный файл убирается, исходное исключение пробрасывается,
  цель остаётся нетронутой. Тихого отката на прямую запись нет сознательно — он вернул бы ровно тот
  дефект (обрезанный файл), ради которого модуль существует.
- **Граница гарантии: обрыв процесса, но не потеря питания.** `fsync` файла и каталога не делается:
  генерация создаёт десятки файлов за операцию, а защищаемый класс отказа — прерванная запись
  (исключение, kill), а не отказ диска. Не описывать эту защиту как «durable».

Кто пишет через него: `writeTextFilePreservingBomAndEol` (`infra/xml/XmlUtils.ts`) делегирует сюда — то
есть все редакторы существующего XML получили атомарность без правок; `HashCache` и `MetadataCache` лишились
собственных копий temp+rename; `CfeBorrowService` — все создания новых файлов. **Единственная реализация
temp+rename в проекте** — до модуля их было две, и каждая новая запись плодила третью; новый писатель файла
выгрузки обязан идти через `writeFileAtomic`/`writeTextFilePreservingBomAndEol`, а не своим `rename`.

**Почему это не одна механика со staging-схемой выгрузки CF** (см. паттерн `/DumpCfg` выше). Внешне похоже
(временный файл в том же каталоге + перенос), но отличается по сути: в staging-схеме файл пишет ЧУЖОЙ процесс
(Конфигуратор), а решение о переносе принимает политика кода возврата (`exitCode === 0`), а не факт
завершения записи; при сбое платформа всё равно оставляет мусор. `writeFileAtomic` пишет строку из
памяти сам и переносит безусловно, если запись удалась. Обобщение в один примитив скрыло бы это различие и
потянуло бы политику `exitCode` в чистый модуль записи.

`CfeBorrowService` — ловушка «эталон стиля». Три места перезаписи существующего файла переведены на
`writeTextFilePreservingBomAndEol(file, originalXml, nextXml)` (раньше писали `writeFileSync` и теряли
BOM/EOL, запрет №12). Исходное содержимое ОБЯЗАНО запоминаться отдельной константой до `replace`: если
передать писателю уже изменённый текст как «оригинал», BOM и стиль переводов строк «сохраняются» с самого
результата, и сохранение становится пустой операцией.

### Два механизма подавления собственных файловых событий

`Container` игнорирует часть событий `FileSystemWatcher`, спровоцированных им же самим (генерация
XML, импорт/обновление конфигурации в базе). Механизма два, у них разная гранулярность, и они гасят
РАЗНОЕ — путать их нельзя:

- **`suppressedConfigurationReloads`** (`Map<нормализованный путь файла, expiresAt>`, поле
  `Container`) — пофайловый. Гасит только перестройку кэша дерева
  (`scheduleTreeCacheRefresh` → `refreshTreeCacheForFiles`) по конкретным записанным файлам:
  расширение только что сериализовало XML само и знает его новое содержимое, повторный парсинг
  того же файла из события watcher избыточен.
- **`ConfigurationCleanWindow`** (`infra/fs/ConfigurationCleanWindow.ts` — чистый класс без
  `vscode`, источник времени внедряется конструктором ради тестируемости истечения окна без
  реального таймера) — по КОРНЮ конфигурации. Открывается в `Container.markConfigurationsClean`
  сразу после успешного импорта/обновления конфигурации в базе, на
  `ConfigurationCleanWindow.defaultDurationMs` (15 секунд). Пока окно открыто,
  `scheduleChangedConfigurationStateRefresh` игнорирует событие watcher по файлу этого корня
  ЦЕЛИКОМ — ни быстрая пометка «конфигурация изменена» по одному файлу, ни планирование полного
  пересчёта. Причина: `FileSystemWatcher` доставляет события файлов, записанных импортом, уже
  ПОСЛЕ завершения операции — быстрый путь снова помечал только что синхронизированную
  конфигурацию изменённой, и расширение сразу предлагало обновить базу повторно. Полный пересчёт
  (`ConfigurationChangeDetector.detect`) даже с быстрой проверкой по stat-мемо (см. «Хеш-кэш:
  базовая линия и stat-мемо» ниже) стоит O(число файлов) вызовов `stat` (≈100 тыс. на БП 3.0),
  а сразу после импорта — ещё и перехеширование файлов, которые импорт переписал. Поэтому гонять
  его на каждое из тысяч запоздавших событий watcher нельзя. По закрытии окна
  `markConfigurationsClean` сам ставит РОВНО ОДИН авторитетный `refreshChangedConfigurationState()` —
  так правка, сделанная пользователем во время окна, не теряется, а полный пересчёт не дублируется
  на каждое событие.

Окно тишины гасит ТОЛЬКО события watcher. Сам `markConfigurationsClean` вызывает
`changeDetection.invalidate()`, и если в этот момент шёл фоновый прогон, повтор стартует сразу, не
дожидаясь закрытия окна. Это осознанно: прогон, начатый до записи новой базовой линии импортом,
отбрасывается, а повтор сравнивает уже с новой линией. Цена — одна лишняя `stat`-проверка.

Новый код, который сам пишет файлы выгрузки и не должен ложно взводить «конфигурация изменена
относительно базы», использует `cleanWindow` через `markConfigurationsClean`, а не заводит третий
параллельный механизм подавления.

### Хеш-кэш: базовая линия и stat-мемо

«Конфигурация изменена относительно базы» решается сравнением SHA-1 содержимого файлов выгрузки
(`*.xml`, `*.bsl`, макеты; критерий — `isSupportedConfigFile`) с базовой линией. Раньше каждая
проверка читала и хешировала ВСЮ выгрузку: на БП 3.0 (104 тыс. файлов, 7,5 ГБ) старт расширения
блокировал Extension Host на 4+ минуты (разбор — [plans/startup-hash-detect.md](./plans/startup-hash-detect.md)).
Теперь данные разделены на два файла с разной ответственностью.

| | Базовая линия | Stat-мемо |
|---|---|---|
| Модуль | `infra/cache/HashCache.ts` | `infra/cache/HashStatMemo.ts` |
| Файл | `.v8vscedit/cache/<sha1(scopeKey)>.json` | `.v8vscedit/hash-stat/<sha1('stat::' + нормализованный configDir)>.json` |
| Смысл | Состояние, загруженное в БД (`files: Record<путь, sha1>`, `schemaVersion: 1` — формат не менялся) | Факт о содержимом: «файл с отпечатком (mtime, ctime, size) имел sha1 H» |
| Ключ | Область (`cf::…`/`cfe::…`, у агента — `''`) | Каталог выгрузки (общий для detect, CLI и агента) |
| Кто пишет | Импорт (`importGitChanges`, `importConfiguration`, `refreshHashCache` — CLI), `AgentSyncEngine.saveBaseline`; `detect` — ТОЛЬКО при первичной инициализации, если линии нет | Любой проход `scanHashSnapshot` с `projectRoot`, если мемо изменился |

**Почему мемо — отдельный файл, а не поле базовой линии.**
- Детектор не должен переписывать базовую линию. Иначе возникает гонка: `detect` прочитал старую
  линию → CLI записал новую после импорта → `detect` записал старые `files` со свежими stat. Итог —
  потерянная базовая линия импорта и ложное «изменено» или неверная частичная загрузка. Мемо хранит
  только факты о содержимом, поэтому его запоздалая перезапись безвредна: теряется лишь скорость.
- `AgentSyncEngine.saveBaseline` пишет литерал `{ schemaVersion: 1, …, files }` и стирал бы чужое поле
  при каждой операции агента.
- Потребители `files` (CLI, `SyncManifest.loadSyncManifest`, `patchHashSnapshot`, `diffHashSnapshots`)
  не меняются.

**Миграция.** Старый проект мемо не имеет: первый проход один раз хеширует все файлы, результат
сравнивается с сохранёнными sha1 — ложных изменений нет, файл базовой линии остаётся байт-в-байт
прежним, появляется файл мемо. На больших выгрузках этот первый проход долгий, но идёт в фоне.

**Алгоритм прохода** (`infra/cache/HashScanner.ts`, `scanCurrentHashes`/`scanHashSnapshot`):
1. Момент старта прохода берётся ДО любого `stat`/`read`.
2. Асинхронный обход каталогов на `fs.promises` с пулом `HASH_SCAN_CONCURRENCY = 16` — поток
   Extension Host свободен. Больше 16 не берём: пул libuv — 4 потока, операции ФС других расширений
   не должны надолго вставать в очередь.
3. Для файла: `stat` → если mtime, ctime и size совпали с записью мемо, хеш берётся из мемо, файл НЕ
   читается. Иначе (новый файл, другой отпечаток, битая запись) — `readFile` + SHA-1 (`hashContent`).
   Порядок «`stat` до чтения» обязателен: изменение после `stat` сдвинет отпечаток вперёд, и
   следующий проход увидит несовпадение.
4. «Изменено» по-прежнему решает только хеш (`diffHashSnapshots`): после `touch`/`git checkout` с
   прежним содержимым файл перехешируется, хеш равен базовому, изменения нет, а отпечаток в мемо
   обновляется.
5. ctime в отпечатке ловит инструменты, восстанавливающие mtime при том же размере (robocopy
   `/COPY:T`, распаковка с сохранением времени): на Windows `ctimeMs` — NTFS ChangeTime, `utimes` его
   не откатывает.
6. Удалённые файлы выпадают из мемо сами: новый мемо собирается только из существующих файлов.
   Мемо пишется (через `writeFileAtomic`) только если изменился; сбой записи мемо не роняет проверку
   (`HashScanReport.memoSaveError`) — мемо лишь оптимизация.

**Racy-mtime** (`isRacyFingerprint`, по образцу racy-git): отпечаток, у которого
`max(mtime, ctime) > старт прохода − HASH_STAT_RACY_WINDOW_MS` (3000 мс), в мемо НЕ сохраняется —
следующий проход перечитает файл. Запись в файл в ту же единицу времени ФС, что и снятие отпечатка,
иначе дала бы тот же mtime и пропуск изменения. 3 с покрывают FAT32 (2 с) и HFS+/ext3 (1 с) с
запасом; NTFS — 100 нс. Время в будущем (сетевая ФС с расхождением часов) всегда racy: корректность
сохраняется, страдает скорость — диагностика по счётчикам `racy`/`hashed` в строке
`[hash-cache] <имя>: файлов N, перехешировано M (racy K), T мс` канала «1С Редактор».

**Ошибки ФС.** `ENOENT`/`ENOTDIR` (файл или каталог исчез между `readdir` и `stat`/`readFile`)
эквивалентны отсутствию файла. Остальные коды (`EBUSY`, `EACCES`, `EPERM`, `EISDIR`) пробрасываются:
пропуск заблокированного файла превратил бы его в «удалённый», и частичная загрузка ушла бы с
удалением.

**Фоновая проверка в расширении** (`infra/fs/ChangeDetectionRunner.ts`, чистый класс без `vscode`;
вынесен из `Container`, потому что `Container` не инструментируется c8):
- `request()` — single-flight: в простое запускает прогон, во время прогона ставит РОВНО ОДИН повтор
  (сколько бы запросов ни пришло). Конфигурации берутся при старте каждого прогона, поэтому повтор
  подхватывает новый состав.
- `invalidate()` — результат идущего прогона отбрасывается и ставится повтор. Вызывается из
  `markChangedConfiguration` (иначе прогон, начатый до правки, затёр бы оптимистичную пометку своим
  «0 изменений») и из `markConfigurationsClean` (см. выше).
- `whenIdle()` — ждёт окончания прогона и всех повторов. `Container.getChangedConfigurations` стал
  `async` и ждёт его: без этого команда «Обновить конфигурации» в окне фоновой проверки ответила бы
  ложным «Изменений не обнаружено» и пропустила загрузку в БД. Следствие: при первой миграции
  большой выгрузки команда держит флаг занятости `isUpdatingConfigurations` до конца фоновой
  проверки (минуты; прогресс «проверка изменений» показывается) — осознанно, корректность важнее.
- `dispose()` — в `context.subscriptions` и в `deactivate()`: результат идущего прогона не
  применяется, повторы отменяются.
- `v8vscedit.hasChangedConfigurations` выставляется в `apply` (авторитетный результат), а также в
  `markChangedConfiguration`/`markConfigurationsClean`. До первого результата после старта контекст
  ложен — дерево показывается из кэша сразу, отметка появляется после фоновой проверки.

Первичная инициализация базовой линии (бывший `ConfigurationChangeDetector.ensureCaches`) живёт
внутри `detect`: нет линии → повторная проверка (не записал ли её CLI за время прохода) → запись
текущего снимка, результат для конфигурации — «0 изменений». Порядок «кэш готов → сравнение»
обеспечен по построению: оба шага в одном прогоне, а single-flight исключает параллельный прогон.
Метаданная часть `ensureCaches` удалена как избыточная: `MetadataTreeProvider.buildConfigNode` сам
загружает снимок дерева и при его отсутствии строит (`saveMetadataCacheForEntry`) — раньше снимок
(~111 МБ на БП) грузился на старте дважды.

**Потребители.**

| Потребитель | Путь |
|---|---|
| `ConfigurationChangeDetector.detect` (расширение) | `scanHashSnapshot` с мемо |
| CLI `importGitChanges`, `refreshHashCache`, `importConfiguration` (режим Full) | `scanHashSnapshot` с мемо (`cli/core/hashCache.ts` — re-export) |
| `SyncManifest.buildSyncManifestFiles` (манифест B агента; `SyncContext.projectRoot`) | `scanHashSnapshot(projectRoot, '', configDir)` |
| `collectCurrentHashes`, `patchHashSnapshot` (частичная загрузка) | Без мемо — читают только переданный список, уже O(изменения) |
| `buildHashSnapshot` | Эталонный синхронный полный проход без мемо: оракул эквивалентности и построитель фикстур в тестах; в production не вызывается |

## Удалённый сервер 1С

Расширение умеет работать с базой, которая обслуживается на сервере 1С, а не на машине разработчика.
Пользовательская инструкция по настройке — [remote-designer.md](./remote-designer.md); исторический
план с обоснованиями и замерами пилота — [plans/remote-designer-plan.md](./plans/remote-designer-plan.md)
(ссылки «Нxx» и «§5b п.N» ниже — оттуда).

Включается парой настроек: `v8vscedit.configuration.operationMode = agent` и
`v8vscedit.agent.location = remote`. Режим `batch` вместе с `remote` — явная ошибка конфигурации
(`getAgentExecutionMode`), а не молчаливый откат на локальный запуск: операция пошла бы не на той
машине и, возможно, не с той базой.

### Схема

```
VS Code (расширение)                                   сервер 1С
 ├─ SSH-shell ───────────────────────────────────────► 1cv8 DESIGNER /AgentMode (агент конфигуратора)
 │   команды config dump/load, common connect-ib …        │  персональный корень агента
 ├─ SSH+SFTP (ОТДЕЛЬНОЕ соединение) ───────────────────► ─┘  workspace/<projectId>/cf|cfe/<имя> (M)
 │   обмен файлами выгрузки, архивы, list-файлы              exchange/, lists/
 └─ хост powershell.exe ──► New-PSSession (WinRM) ─────► 1cv8 DESIGNER (пакетный: хранилище)
     протокол «строка JSON ↔ строка с маркером»             <TEMP>\v8vscedit-*  (входные/выходные файлы)
```

Две независимые цепочки:

- **Агент конфигуратора** (`infra/agent/**`) — операции над выгрузкой и базой: импорт БД → проект,
  загрузка проект → БД, обновление БД. Агент запускается на сервере вне расширения; расширение
  подключается к нему по SSH.
- **Пакетный 1cv8 на сервере** (`infra/process/remote/**`) — операции хранилища конфигурации.
  Агент не даёт команд хранилища, а локальный 1cv8 не видит ни серверных путей, ни хранилища по
  серверному UNC. Поэтому тот же запрос, что исполняется локально, исполняется на сервере через
  PowerShell-сессию (PSSession по WinRM).

Соединения SSH и SFTP — РАЗНЫЕ: агент даёт один канал на соединение (`sftp` вторым каналом рядом с
shell даёт «Unable to start subsystem: sftp», shell после sftp — «Unable to open shell»; пилот §5b п.2).
SFTP открывается отдельной фабрикой (`connectSftpAgentFileStore`, `infra/agent/files/SftpConnection.ts`)
с той же политикой повторов, но своим экземпляром цикла (Н31/Н49).

### Модель синхронизации M / P / B

На каждую цель (`cf` или `cfe/<имя>`) есть четыре сущности:

| Сущность | Что это |
|---|---|
| **БД** | конфигурация в базе |
| **M** | серверное зеркало: каталог выгрузки в персональном корне агента `workspace/<projectId>/cf` или `…/cfe/<имя>` (`AgentWorkspaceService`). `projectId` — короткий хэш корня проекта: персональный корень один на пользователя агента, а одну базу могут открыть два окна |
| **P** | выгрузка в проекте (`src/cf`, `src/cfe/<имя>`) |
| **B** | базовая линия: манифест «относительный путь → sha1» отслеживаемых файлов P на момент последней успешной операции + флаг состояния M (`fresh` / `stale` / `empty`) и полнота M (`mirrorCoverage`: `full` / `sparse`, см. ниже). Лежит в `<корень проекта>/.v8vscedit/agent-sync/<sha1(scope)>.json`, пишется через `writeFileAtomic` (`SyncManifest.ts`) |

Инвариант после любой успешной операции: P ≡ M по отслеживаемым файлам и B = hash(P). B — ВНЕ
каталога агента по умолчанию (`.v8vscedit/agent`): агент вправе его чистить, а пользовательский
`/AgentBaseDir` может указывать куда угодно (Н38). Набор отслеживаемых файлов и хэш — те же, что у
`HashCache` (`buildHashSnapshot`), критерий один.

Решения принимает чистый `SyncPlanner` (`infra/agent/sync/SyncPlanner.ts`), исполняют
`AgentImportFlow`/`AgentLoadFlow` через `AgentFileStore` и команды агента; `AgentSyncEngine` — фасад.
Запись в проект — только через `writeFileAtomic` (`applyProjectChanges`), перед записью вызывается
`onProjectFilesWillChange(changed)` (подавление собственных файловых событий, см. ниже).

**Импорт (БД → P).**

- Локальный агент (`store.kind === 'local'`): `dump --update --force` в M, затем ПОЛНОЕ сравнение M и P
  (хэширование локально дёшево), запись только реально изменённых файлов, исчезнувшие удаляются.
- Удалённый агент, M `empty` (первый раз, манифест отсутствует или в M нет `ConfigDumpInfo.xml`):
  ОДНА серверная выгрузка — `dump --archive` в `exchange/<op>` (раньше было две: полная в M и ещё раз
  архивом), скачивание архива в локальный файл и потоковая распаковка в P. Зеркало M при этом
  **засевается** из архива (`MirrorSeed`): в M кладутся только `ConfigDumpInfo.xml` (запись архива) и
  `Configuration.xml`, M становится `fresh` и `sparse`. Альтернатива — посев из выгрузки проекта: если в
  P есть пригодный `ConfigDumpInfo.xml` (проверка `inspectProjectMirrorSeed`: тот же вид и имя
  конфигурации, иерархический формат, известная версия формата, версия совпадает с `Configuration.xml`),
  пользователю задаётся вопрос (хук `confirmMirrorSeed`, `mirrorSeedPrompt.ts`): «Использовать
  выгрузку проекта» — серверная выгрузка не нужна вовсе, дельта берётся относительно файла версий
  проекта и скачиваются только объекты, изменённые в базе после него; «Полная выгрузка» — самопосев из
  архива; закрытие диалога — отмена. Нет хука (MCP) — всегда `full`.
- Удалённый агент, M есть — дельта в ДВА шага (пилот §5b п.4: `--get-changes` вместе с `--update`
  ничего не выгружает, только пишет список): `dump --update --get-changes=F` → разбор списка →
  `dump --update` (обновляет M). Строки списка — `New|Modified: <EnglishKind>.<Name>[.<Часть>]` (по
  ОБЪЕКТАМ, не по файлам); перевод в файлы — по владельцу верхнего уровня через `META_TYPES`
  (`ChangedObjectFiles`): `<Folder>/<Name>.xml` + всё поддерево `<Folder>/<Name>/` из SFTP-листинга.
  Файлы C ∪ D (C — по списку, D — локальные правки P относительно B, которые импорт обязан перетереть)
  скачиваются параллельно (`agent.transferConcurrency`); локальные файлы владельцев, которых нет в M,
  удаляются.
- **Две фазы решений.** Фаза 1 — чистая `planBeforeUpdate`, ДО `dump --update` (по `mirrorState` и
  списку изменений); фаза 2 — `planRemoteImport`, ПОСЛЕ него (владельцы, порог, грязные файлы). Причины
  полной выгрузки (`ImportArchiveReason`) — ДАННЫЕ в таблице `ARCHIVE_REASON_POLICY` (`SyncPlanner.ts`):
  фаза, «засевать ли M из архива», текст причины. Новая причина — строка таблицы, а не ветка потока.

  | Причина | Фаза | Самопосев M | Когда |
  |---|---|---|---|
  | `mirror-empty` | до | да | M пуст, посев из проекта не принят/невозможен |
  | `full-dump` | до | да | список `FullDump` (любое удаление/переименование — других признаков платформа не даёт) |
  | `unrecognized` | до | да | неизвестный `Change` или часть — консервативно |
  | `unresolved-objects` | после | нет | владелец списка не нашёлся в M |
  | `over-threshold` | после | нет | файлов больше `agent.archiveThresholdFiles` (по умолчанию 20000; защита, а не рабочий путь) |
  | `sparse-mirror-dirty` | после | нет | ЗАПАСНАЯ: точечное восстановление не удалось |

  Причины фазы 1 выполняются ОДНОЙ выгрузкой без `dump --update` (раньше `--update` мутировал/перезаписывал
  M зря, и выгрузок было две): архив + самопосев M из архива. Архив — стандартный zip (deflate, бит
  UTF-8), распаковывается собственным `ArchiveCodec`/`ZipContainer` (включая zip64) ПОТОКОМ из локального
  файла: скачивается через `downloadToFile`, читается случайным доступом (`ZipByteSource`), буфера размером
  с архив нет нигде. Два прохода: валидация и сравнение, затем запись — битый архив не оставляет P
  наполовину обновлённым.
- **Вопрос перед полной выгрузкой** (хук `confirmFullDump`, `fullDumpPrompt.ts`; нет хука — MCP — всегда
  `'dump'`). Для причин фазы 1 задаётся ДО мутаций M и манифеста (отказ ничего не оставляет); для фазы 2 M
  уже обновлён, поэтому отказ пишет манифест `empty` + текущую полноту (общий путь `runOperation`). Отказ —
  `AgentFullDumpDeclinedError` (подкласс отмены) с инструкцией ручной выгрузки. Выбор «Полная выгрузка» в
  вопросе о посеве считается ответом и второй раз не спрашивается. Путь загрузки (`AgentLoadFlow`,
  `prepareMirror: 'full-dump'`) вопроса пока не имеет — бэклог плана.
- **Точечное восстановление** (`SparseRestore.restoreFromDatabase`, вариант А, эксперименты 11–12 в
  [плане §5b](./plans/remote-designer-plan.md)). Если у неизменённого владельца в разреженном M нет файлов,
  а локально они правлены/удалены, план даёт дельту с `restoreFromDatabase`. Имена объектов берутся из
  `ConfigDumpInfo.xml` ПРОЕКТА (`ConfigDumpInfoIndex`, весь файловый набор владельца), записываются в список
  `exchange/<op>.objects.txt` (BOM UTF-8, LF), и выполняется `dump --list-file` (без `--update`: вместе
  агент их не принимает) в каталог `exchange/<op>/restore`, НЕ в M: M и его полнота не меняются,
  `markMirrorMutated` не нужен. Скачиваются только нужные файлы. Любой отказ агента/неразрешимое имя —
  результатом `ok: false` → запасной архив `sparse-mirror-dirty` (с вопросом); P к этому моменту не тронут.
  Транспортные сбои и отмена — исключения.
- **Дельта без буфера в памяти.** Скачанные файлы пишутся в staging-файлы локального обмена `delta-N`
  (`LocalExchange`), а не держатся в `Map`: при пороге в десятки тысяч (средний файл БП ≈ 72 КБ) иначе
  гигабайты в памяти. STAT/LIST — пулом `forEachConcurrent`/`statFiles` (`AgentFileTransfer`,
  `agent.transferConcurrency`), как передача файлов: последовательные запросы по 80 мс на сотнях владельцев —
  минуты. Перевод «объект → файлы» — `ownerOfProjectFile` (`ChangedObjectFiles.ts`): обратная карта
  папка → вид, ВЫВЕДЕННАЯ из `META_TYPES` (второго словаря нет).
- **Индекс `ConfigDumpInfo.xml`** — `infra/xml/dumpInfo/ConfigDumpInfoIndex.ts`
  (`parseConfigDumpInfoIndex`/`readConfigDumpInfoIndex`): единственный разбор файла версий (владельцы
  верхнего уровня и их записи). Посев, сироты и точечное восстановление читают его, а не регулярками.
- **Ручная замена выгрузки проекта.** Отпечаток `ConfigDumpInfo.xml` проекта (`sha1` + `size` + `mtimeMs`,
  `ProjectDumpInfo.ts`) хранится в манифесте и пишется только после УСПЕШНОГО импорта (в т. ч. архивного,
  который сам пишет этот файл); при совпадении size+mtime файл не перечитывается. При непустом M расхождение
  отпечатка → причина посева `project-replaced`, тот же вопрос `confirmMirrorSeed`; отсутствие отпечатка
  (старый манифест) замены не означает. После посева из проекта — поиск «сирот» (`ProjectSeed`): файлы
  владельцев верхнего уровня, которых нет в CDI проекта и в списке изменений; удаление — только по
  `confirmOrphanRemoval` (нет хука — MCP — сообщение в журнал, файлы остаются), до расчёта B.
  Без UI (MCP) умолчания: полная выгрузка без вопроса, сироты не удаляются.

**Полнота M (`mirrorCoverage`).** Ортогональна `mirrorState`: `full` — в M все файлы выгрузки,
`sparse` — только посев (файл версий, `Configuration.xml`) и файлы владельцев, изменённых после посева
(`dump --update --force` дописывает ровно их файлы, побайтно равные полной выгрузке — пилот §5b п.19).
Инвариант разреженного M: присутствующий файл равен БД, ОТСУТСТВУЮЩИЙ НЕ ОЗНАЧАЕТ НИЧЕГО (ни удаления,
ни ошибки перевода). Следствия для планировщика: в `changedFiles` попадают только файлы, реально
присутствующие в M; из P удаляются только файлы, которых нет ни в B, ни в M после `--update`
(`deletableIfAbsent`), а не все отсутствующие в M. Манифест без поля = `full` (старые манифесты писались
только при полном M); НЕИЗВЕСТНОЕ значение поля делает манифест непригодным (принять его за `full`
значило бы удалять файлы по отсутствию в разреженном M). Любая мутирующая операция, оборвавшаяся
сбоем, пишет в манифест ТЕКУЩУЮ полноту, а начатый посев сразу делает M `sparse` — оборванный посев
не выдаст себя за полное зеркало. `full` ставит только полная выгрузка в M без `--update`
(`prepareMirror: 'full-dump'`, локальные стратегии).

**Посев из проекта и расхождение P с БД.** При посеве из проекта B := hash(P): ручные правки XML,
сделанные в проекте после той выгрузки и не загруженные в базу, войдут в базовую линию и НЕ попадут
в загрузку «по изменениям» — расхождение P и БД сохраняется до полной загрузки. Поэтому согласие
пользователя обязательно, а у MCP-инструментов параметра согласия нет: агент не может осознанно принять
скрытое расхождение, MCP всегда работает как `full`. Чужой или устаревший файл версий проекта (другая
база, Н42) безопасен: `--get-changes` относительно него даёт сверхприближение или `FullDump` → порог/
архив — это самопроверка посева.

**Потоковый архив.** Скачивание/отправка — `AgentFileStore.downloadToFile`/`uploadFromFile`
(`AgentFileTransfer` — конкурентная передача с отменой; SFTP — `SftpChunkedIo`, окно запросов,
`IO_CHUNK` = 31 КиБ: ssh2 для не-OpenSSH сервера, каким является libssh агента 1С, ограничивает данные
одного запроса 34000 − 2048 = 31 952 байтами; 32 КиБ ломает чтение/запись). Запись zip —
`ZipStreamWriter` (запись файлов P по одному, без буфера архива). Файловый источник (`ArchiveFile`)
сверяет size+mtime на каждом чтении: подмена архива посреди операции — отказ. Пределы разбора:
`MAX_CENTRAL_DIRECTORY` (256 МБ), `MAX_ENTRY_SIZE` и `compressedSize` записи (1 ГБ), степень сжатия.
Прогресс скачивания — в журнал: каждые 10% или каждые 16 МБ, если размер неизвестен. Локальный каталог
обмена — `<корень проекта>/.v8vscedit/agent-exchange/<префикс цели><число>` (`LocalExchange`): штатно
его убирает `dispose`, после аварийного завершения процесса — `pruneStaleLocalExchanges` на старте
следующей операции той же цели (по маске «префикс + только цифры», чужие каталоги не трогаются).
`writeFully` (`infra/fs/FileHandleWrite.ts`) — цикл дозаписи по `bytesWritten` для позиционной записи
в файл: `FileHandle.write` вправе записать меньше запрошенного. Это НЕ замена `AtomicFileWriter`
(временный файл + rename), а механика записи внутри него и в потоковом писателе.

**Отмена.** `AgentTransferCancelledError` (слой `files/`) → `AgentSyncCancelledError` через
`withTransferCancellation` (`SyncContext.ts`); в UI это «операция отменена», а не ошибка.

**Загрузка (P → БД).**

| Состояние | Действие |
|---|---|
| diff(B, P) пуст | `skipped` |
| нет B (`no-baseline`), есть удаление или переименование (частичная загрузка удалений не передаёт), изменённых файлов выше порога | полная загрузка: локальный агент — M := копия P и `load --dir=M --update-config-dump-info`; удалённый — zip всего P → SFTP → `load --archive` (M становится `stale`) |
| обычная частичная | подготовка M (`prepareMirror`) → изменённые и добавленные файлы в M → list-файл (BOM UTF-8, LF) → `load --partial --list-file --no-check` |

`prepareMirror` перед частичной загрузкой: `none` (M свежий); `full-copy` (локальный M пуст — копия P
целиком); `refresh-dump` (M `stale` после
загрузки архивом: БД ≡ P, достаточно `dump --update` на сервере без скачивания); `full-dump`
(удалённый M потерян, но B известна и БД ≡ B: M очищается и выгружается на сервере целиком без
скачивания, Н47). `--update-config-dump-info` при частичной загрузке НЕ передаётся: конфигуратор
перезаписывает файл версий «срезом» и на следующей частичной загрузке падает в пустой `UnknownError`.
Сочетание `--update` + `--archive` агент не выполняет — guard в `AgentCommand`.

Прочее: имя `--archive` агент разрешает ОТНОСИТЕЛЬНО `--dir` (пилот п.6, 15); каталоги файлов
`--get-changes`/`--list-file` агент сам не создаёт (создаются через SFTP `mkdir` до команды); `rmdir`
непустого каталога на SFTP агента удаляет рекурсивно — `AgentFileStore.remove` без `recursive`
проверяет пустоту сам; `rename` на агенте перезаписывает цель (нестандартно для SFTP v3), для
стандартных серверов есть резервная схема (Н30). Каталог обмена `exchange/<op>` убирается в `finally`.

### Жизненный цикл подключения ИБ

`AgentInfoBaseSession` (`infra/agent/`) — единственный владелец состояния «база подключена к агенту».

- Подключение ИБ (`common connect-ib`) держится МЕЖДУ операциями: цикл «загрузить → обновить БД →
  загрузить» платит `connect-ib` один раз. Оно НЕ переживает закрытие SSH-сессии (пилот п.1), поэтому
  SSH тоже живёт между операциями, а любой сброс SSH сбрасывает и флаг «подключено»: после обрыва
  открывается новый транспорт и следующая операция делает `connect-ib` заново (ответ «уже подключено»
  принимается как успех).
- Все обращения к агенту идут одной очередью (агент однопоточен): `release` перед пакетной операцией
  не вклинивается в середину операции.
- Ошибка операции — консервативно: `disconnect-ib` (ошибка «не подключено» проглатывается), сброс SSH.
- `v8vscedit.agent.idleDisconnectMinutes` (по умолчанию 0 — выключено): после простоя сессия сама
  делает `disconnect-ib`. Явная точка отпускания — команда `v8vscedit.agent.releaseInfoBase`.
- **Release перед пакетными операциями.** Подключённая к агенту ИБ блокирует пакетный 1cv8 и
  интерактивный Конфигуратор. Поэтому каждый раннер пакетного Конфигуратора (`runInternalCliCommand`,
  `RepositoryCommandRunner`) перед запуском вызывает `releaseAgentInfoBaseForBatch`
  (`ui/commands/ext/agent/AgentServiceRegistry.ts`): есть кэшированный сервис — `disconnect-ib`;
  нет, но включён агентский режим — порт агента проверяется (до 500 мс) и найденный внешний агент
  отключается принудительно (`force`: после перезапуска VS Code внешний агент мог остаться
  подключённым). По пилоту п.1 принудительное отключение избыточно (свежая SSH-сессия заведомо не
  подключена), но оставлено как безопасное по умолчанию — цена одна проверка порта на операцию (Н18).
  Ошибка освобождения — отказ запуска: пакетный Конфигуратор упёрся бы в блокировку.
  Переподключение после операции НЕ делается — оно ленивое, при следующей агентской операции.
  Интерактивный Конфигуратор (`InteractiveDesignerLauncher`) отпускает базу так же и переподключает её
  после закрытия.
- `runWithInfoBaseReleased` (`BatchDesignerGuard.ts`) в продуктовом коде не используется: раннеры
  вызывают `releaseAgentInfoBaseForBatch` и запускают операцию отдельно (Н17). Порядок
  «release → запуск» обязателен.
- Мутирующие операции берут `configurationOperationLock`; сброс кэша сервисов агента при смене
  `v8vscedit.agent.*`/`v8vscedit.remote.*` откладывается до его освобождения
  (`agentSettingsWatcher`, Н48).

### Повтор `connect-ib` при блокировке ИБ

Сразу после пакетной операции 1cv8 (хранилище, CF/CFE) база может быть ещё занята: освобождение —
доли секунды, на клиент-серверной базе при обрыве соединения — секунды. Агент отвечает на такой `connect-ib`
финальным `error` с `error-type: DesignerAlreadyStarted` («Ошибка блокировки информационной базы для
конфигурирования»; эксперимент 13). `AgentInfoBaseSession` повторяет `connect-ib` по чистой функции
`decideInfoBaseLockRetry` (`domain/agent/InfoBaseLockRetryPolicy.ts`): окно 15 с от первого отказа,
задержки 0,5 → 1 → 2 с (дальше последняя), попытка, которая началась бы на границе окна или позже, не
делается; в журнал — «База занята… повторяю». Классификация — по `error-type`, текст — фолбэк только для
ответа без него. Повтор не привязан к «недавней пакетной операции этого процесса»: держателем может быть
пакетный 1cv8 по PSSession, другое окно VS Code или CLI. Окно исчерпано — `AgentInfoBaseLockedError` с
сообщением про причину (открытый Конфигуратор, стартер вместо 1cv8, незавершённая операция). Ограничения:
отмена в паузе между попытками замечается только после следующей попытки; на клиент-серверной базе окно
не замерено (Э15, ручной пилот).

### Политика готовности SSH

Агент открывает порт раньше, чем начинает принимать логин, и на тяжёлой серверной конфигурации даёт
«Permission denied» сразу после старта. Серия неудачных входов под логином 1С недопустима
(блокировки), поэтому повторы — по чистой функции `decideAgentConnectRetry`
(`domain/agent/AgentConnectPolicy.ts`), цикл исполняет `AgentConnectRetry`, ошибку классифицирует
`SshConnectErrorClassifier` (`refused`/`auth`/`timeout`/`network`/`other`):

- `refused` — повторять в окне `startupTimeoutMs`; иначе «недоступен»;
- `auth` — повторять только если есть опорная точка («агент только что поднялся»: старт собственного
  процесса или наблюдённый `refused`) и окно `authWarmupMs` не вышло; без опорной точки — сразу
  «неверные учётные данные», одна попытка;
- `timeout`/`network` — в окне `startupTimeoutMs` и только при опорной точке; `other` — сразу ошибка.

Для внешнего (серверного) агента момент старта неизвестен: окно прогрева открывается лишь после
собственного наблюдения `refused`. **`startupTimeoutMs` играет две роли:** ожидание открытия SSH-порта
после запуска собственного агента (`waitForTcpPort`) и окно повторов `refused`/`timeout`/`network` в
политике. Диагностика (`checkConnection`) использует нулевую политику — одна попытка на часть.

### Хост PowerShell и удалённые операции хранилища

`DesignerBatchExecutor` (`infra/process/designer/`) — единый интерфейс пакетного 1cv8: запрос
(`DesignerBatchRequest`) содержит аргументы БЕЗ исполняемого файла и БЕЗ `/Out`, входные и выходные
файлы объявлены именами. `LocalDesignerBatchExecutor` исполняет локально, `RemoteDesignerBatchExecutor`
— на сервере; реестр `designerExecutorRegistry` выбирает по `v8vscedit.agent.location`. Вектор
аргументов хранилища строит один `RepositoryDesignerArgs` (UI и CLI), подключение к ИБ —
`InfoBaseConnectionArgs`. Новая пакетная операция обязана идти этим путём (CLAUDE.md,
«Новая пакетная операция Конфигуратора»).

Удалённый исполнитель делает: `mktemp` на сервере → `put` входных файлов (например `ObjectsFile`) →
подстановка серверных путей и `/Out <dir>\out.log /DisableStartupDialogs` → командная строка собирается
в TS алгоритмом libuv (`WindowsCommandLine`) — тем же, что у локального `spawn`, поэтому 1cv8 получает
байт-в-байт тот же вектор → `run` → `fetch` выходных файлов в ЛОКАЛЬНЫЙ staging → `rmtemp` в `finally`.
Перенос staging на путь пользователя делает вызывающий только при `exitCode === 0`.

Хост (`PowerShellRemoteHost`) — один долгоживущий `powershell.exe` на проект (`-EncodedCommand`, текст
скрипта — константа `PowerShellHostScript.ts`), запросы идут последовательной очередью:

- **Протокол** (`PowerShellHostProtocol`): запрос — одна строка JSON в stdin, только ASCII (всё прочее
  `\uXXXX`: кодировку stdin задаёт консоль сервера); ответ — строки stdout с маркером `@@V8VSC@@`,
  остальное — шум PowerShell и уходит в журнал. Операции: `connect`, `mktemp`, `put`, `resolveV8`,
  `run` (события `started{pid}` → `output` → `exit{code, logB64}`), `cancel`, `fetch`, `rmtemp`, `ping`.
  Лог `/Out` передаётся байтами (base64) и декодируется `decodeDesignerLogBytes`.
- **Граница рабочих файлов**: хост работает только внутри `<TEMP>\v8vscedit-*` (проверка на стороне
  исполнения), при `connect` чистит «осиротевшие» каталоги старше суток.
- **Пароль** учётки передаётся только через stdin (`passwordB64`), не в командной строке процесса;
  хранится в SecretStorage, в ключе кэша хоста — его sha256. Неверный пароль (`auth-failed`)
  автоповтором не повторяется, сохранённый пароль стирается (иначе политика домена заблокировала бы
  учётку).
- **Отмена** пользователем: `cancel{id}` идёт в обход очереди, на сервере убивается ДЕРЕВО процессов
  (`taskkill /T /F`: 1cv8 порождает дочерние).
- **Обрыв**: сессия открыта с `IdleTimeout` 10 мин — если `powershell.exe` клиента убит, сервер закроет
  сессию и 1cv8 не будет держать базу вечно (Н61). Безопасные (идемпотентные) запросы
  `ping`/`resolveV8`/`mktemp`/`rmtemp`/`fetch` при `session-broken`/`host-exited` повторяются ОДИН раз
  на новом процессе хоста; `put` и `run` — нет (Н62).
- Если `computerName` пуст, сессии нет и скрипт-блоки исполняются в процессе хоста — режим только для
  тестов (тот же протокол без WinRM).

**Исполняемый файл 1cv8 — только `1cv8.exe`.** Стартер `1cestart.exe` запускает настоящий 1cv8 и сразу
выходит: пакетная операция «завершается» раньше реального конца, следующий `connect-ib` агента упирается в
блокировку. Единая проверка — `infra/process/V8ExecutableGuard.ts` (по имени файла, ошибка
`OnecStarterExecutableError`); вызывается из локального резолвинга (`resolveV8ExecutablePath` в `OnecPlatform`: настройка, поиск по
`PATH`) и серверного (`designerExecutorRegistry`: `remote.v8Path` и ответ хоста `resolveV8` проходят
`assertServerDesignerExecutable` — стартер отвергается, а также любое имя кроме `1cv8.exe`; часть `v8` в
`RemotePowerShellCheck` показывает причину `v8-starter`). Третьей точки резолвинга пути к 1cv8 заводить
нельзя. Ограничение: проверка подключения ловит только стартер, `1cv8c.exe` в ней пройдёт (отказ будет при
самой операции).

В `remote`-режиме **локальными остаются** операции внутреннего CLI (CF/CFE-файлы, пакеты расширений,
список расширений) и интерактивный Конфигуратор. Политика (`decideLocalDesignerInRemote`,
`ui/commands/ext/agent/remoteLocalDesigner.ts`) решает по виду `--ibconnection` из env.json:
клиент-серверная база (`/S`, `Srvr=`) — выполняется локально по сети, в журнал одна строка; файловая
(`/F`, `File=`) и клиент-серверная с петлевым адресом сервера — отказ до побочных эффектов (путь указан
с точки зрения сервера; локальный 1cv8 его не видит или открыл бы другую базу) (Н51).

### Захват объектов хранилища и синхронизация проекта

Платформа при `/ConfigurationRepositoryLock` получает в базу новые версии объектов, изменённых в хранилище
(лог: «Объект получен из хранилища: …»; с `-revised` и без него — Э14), то есть захват меняет основную
конфигурацию, а проект остаётся прежним. Цепочка `v8vscedit.repository.lock`: (вопрос о незагруженных
правках) → захват (`-revised` по `v8vscedit.repository.getRevisedOnLock`, по умолчанию `true`) → импорт
изменённых объектов в проект ТОЙ ЖЕ секцией `configurationOperationLock`. `/UpdateDBCfg` не нужен: агент
после `disconnect-ib` → пакетный захват → `connect-ib` видит новую версию (`--get-changes` точный). Импорт
нужен, если в логе есть «Объект получен из хранилища:» (`hasReceivedFromRepository`,
`infra/repository/RepositoryLockLog.ts`); нераспознанный лог (нет «Начало операции с хранилищем») — импорт
консервативно. Риска молчаливой потери правок проекта нет: в подключённой к хранилищу базе загрузка
незахваченного объекта отклоняется платформой. Если в проекте есть правки, не загруженные в базу, до
замка задаётся вопрос («Загрузить правки в базу, затем захватить» / «Захватить, проект не обновлять» /
отмена; решение — чистая `planRepositoryLock`).

Модули `ui/commands/repository/`: `repositoryLockFlow.ts` (чистые план и исход: `planRepositoryLock`,
`shouldImportAfterLock`, тексты предупреждений), `RepositoryLockCommand.ts` (оркестрация команды),
`repositoryPostSync.ts` (импорт после операции хранилища), `repositoryNodeTargets.ts` (цели узлов дерева
для команд хранилища). Сбой импорта после захвата: отметки захвата сохраняются, предупреждение «выполните
«Импорт конфигурации» до любой загрузки в базу». Тост «Объекты захвачены» показывается всегда;
уведомления внутри секции замка — без `await` (запрет №18).

Прочее из ревью: не более 8 одновременно открытых каталогов SFTP (`RequestLimiter`, общий бюджет OPENDIR
на вложенные пулы); вопрос о полной выгрузке задаётся и на пути загрузки — до очистки зеркала
(`FullDumpConsent`); тексты отказа различаются по контексту (импорт / после посева / загрузка);
`AgentTransferError` несёт действие `transfer`/`stat`/`list`.

### Почему операции хранилища не публикуются как MCP-инструменты

Существующие MCP-инструменты жизненного цикла конфигурации (импорт/обновление/применение) идут через те
же раннеры и сами получают удалённый режим, жизненный цикл подключения ИБ и замок. Хранилище в MCP не
публикуется: его операции меняют ОБЩИЙ для команды внешний ресурс (захват блокирует коллег, помещение
необратимо пишет в историю), требуют интерактивного комментария и подтверждения «обновить перед
помещением», а также пароль хранилища, который MCP-клиент передавать не должен. Отключение агента от
базы — служебное действие, не мутация конфигурации, поэтому тоже не MCP-инструмент.

### Известные ограничения

- **Пароль ИБ в командной строке** (`/P…`) виден в списке процессов сервера — как и локально; это
  ограничение платформы.
- **Ключ хоста SSH не проверяется** (Н50): `buildSshConnectConfig` не задаёт `hostVerifier`, пароль ИБ по
  сети уйдёт любому MITM. Обязательный гейт ДО слияния ветки в `main`: TOFU (отпечаток по `host:port`,
  подтверждение при первом подключении, блокирующий отказ при смене ключа).
- **`ConfigDumpInfo.xml` в P устаревает после дельта-импорта** (Н42): дельта его не скачивает (на
  реальной конфигурации файл 33,7 МБ), обновляют его только архивная ветка и локальное сравнение.
  Инвариант «P ≡ M» нарушен ровно на одном неотслеживаемом файле; пакетный режим файл версий проекта не
  использует, загрузка архивом его не берёт.
- **B отслеживает только `*.xml`/`*.bsl`/`Template.*`** (Н43, критерий `HashCache`): дельта-импорт не
  откатывает локальные правки картинок, справки, `.bin`, а частичная загрузка их не передаёт.
- **Правки базы мимо расширения скрыты после ветки `full-dump`** (Н56): объект, изменённый в базе
  Конфигуратором или другим разработчиком и не изменённый в P, попадает в свежий M, но не в P; B = hash(P),
  M `fresh`, и следующий `--get-changes` его уже не покажет. Данные в базе не теряются (частичная
  загрузка объект не трогает). Обход — удалить манифест цели из `.v8vscedit/agent-sync/`: по коду
  следующий импорт будет архивным, а следующая загрузка — полной (`no-baseline`); на стенде не проверено.
- **Архив > 4 ГБ на запись не поддерживается**: `ZipStreamWriter` пишет zip64-запись числа файлов, но не
  64-битные смещения; граница под защитой с понятным сообщением (7,5 ГБ XML сжимаются примерно до 1 ГБ).
  Чтение zip64 любого размера работает.
- **Разреженный M и правки неизменённых объектов**: восстанавливаются точечно (`dump --list-file`, см. выше);
  архив `sparse-mirror-dirty` — только запасной путь при отказе агента.
- **Ручная замена выгрузки**: признак — отпечаток `ConfigDumpInfo.xml`; при совпадении size+mtime замена не
  ловится. Сироты ищутся только на уровне владельцев верхнего уровня (сироты подобъектов — нет), а «нет в
  базе» фактически означает «нет в CDI проекта»: локально созданный, ещё не загруженный объект попадёт в
  список, поэтому удаление — только по подтверждению. Загрузка после ручной замены даёт сверхприближение
  (расхождение P и БД сохраняется до полной загрузки).
- **Повтор серверной выгрузки после сбоя**: любая мутация M переводит его в `empty` до успеха; после
  обрыва первый импорт повторяет серверную выгрузку (не кэшируется). Известная цена; при согласии на
  посев из проекта повтор дешёвый.
- **Узкое место первого импорта большой конфигурации** (БП КОРП, ~104 тыс. файлов): раньше падало
  «Array buffer allocation failed» на `readFile(full.zip)` и делало две полные серверные выгрузки;
  исправлено потоковой схемой выше.
- **Node 24 и `fs.rmSync` с кириллицей**: на Windows системный Node 24 молча не удаляет файлы с
  кириллицей в имени (пилот п.17) — в синхронизации удаление файлов выгрузки только `unlink`/`rmdir`;
  аудит остальных вызовов `rmSync` — Н37.
- **Два окна VS Code на одном проекте**: замок `configurationOperationLock` действует внутри процесса,
  межпроцессной блокировки нет (сегмент `projectId` разводит только зеркала).
- Удалённая ветка хоста PowerShell (`New-PSSession`, `Copy-Item -FromSession`, `sessionBroken`) тестами
  не исполняется (в тестах `computerName=''`) — проверяется пилотом на сервере (Н58); таймаутов на
  запросы хоста нет (Н60).

```
extension.ts
  └── Container
      ├── infra/*
      ├── ui/tree/*

      ├── ui/readonly/BslReadonlyGuard

```

## Точка входа

`activate()` создаёт `Container` и делегирует ему регистрацию подсистем.

`Container.bootstrap()`:

1. Создаёт инфраструктурные сервисы.
2. Регистрирует дерево, webview-панели, декорации, watcher-ы и команды.
3. Загружает найденные XML-выгрузки конфигураций.
4. Регистрирует `BslReadonlyGuard`.
5. Запускает `LspManager`.

`deactivate()` останавливает активный LSP-клиент через `client.stop()`.

## Ключевые архитектурные решения

| Решение | Обоснование |
|---|---|
| `META_TYPES` как единый реестр типов | Добавление типа метаданных не требует параллельных словарей |
| `MetaPathResolver` как единый resolver путей | Все XML и BSL-модули резолвятся через один инфраструктурный контракт |
| `bsl-analyzer` как единственный LSP | Нет дублирования возможностей и расхождения диагностики между режимами |
| Прямое открытие BSL через `file://` | Внешний LSP работает с реальными файлами, без виртуальной схемы |
| `BslReadonlyGuard` для BSL | Запрет редактирования не зависит от способа открытия файла |
| Ленивая загрузка дерева | Дочерние узлы строятся при раскрытии, а не при старте расширения |
| God-класс → тонкий фасад + подмодули в подпапке слоя | Убирает файлы 1000+ строк без риска регресса: рефактор косметический, публичный API и поведение неизменны (см. выше) |
| MCP-сервер: одна попытка bind, без авто-инкремента порта; конфликт разрешается зондом `/identity` | Авто-инкремент молча подключал агента не к тому проекту; явное `reuse`/`conflict-foreign`/`conflict-unknown` не даёт агенту работать с чужой конфигурацией (см. [mcp-server-lifecycle.md](./mcp-server-lifecycle.md)) |
| `stop()` MCP-сервера форсирует `closeAllConnections()` до `close()` | Долгоживущие SSE-соединения не давали `httpServer.close()` освободить порт естественным путём (см. [mcp-server-lifecycle.md](./mcp-server-lifecycle.md)) |
| Модель трёх деревьев git (HEAD/индекс/рабочее дерево) в представлении изменений | Единственный способ получить непустой diff для staged-файла — сравнивать HEAD↔индекс, а не индекс↔рабочее дерево (см. [git-metadata-changes.md](./git-metadata-changes.md)) |
| Предки объекта в блоке «История» синтезируются из `META_TYPES`, а не берутся из живого дерева навигатора | Живое дерево отражает только текущую рабочую копию и врало бы для исторического состояния коммита (см. [git-history-graph.md](./git-history-graph.md)) |
| Данные из базы (не из XML-выгрузки) передаются CLI → UI через `-ResultFile`, гейт разбора — `exitCode`, а не текст лога | Построчный перекодировщик вывода процесса (`LineBufferedDecoder`) не гарантирует целостность произвольных данных внутри marker-блока; `/Out`-файл — уже устоявшийся канал `*Configuration`-команд (см. «Паттерн: чтение данных из базы через пакетный Конфигуратор» выше) |
| `ConfigurationCleanWindow`: окно тишины по корню конфигурации после импорта/обновления БД, единственный авторитетный пересчёт по его истечении | События watcher по файлам, записанным импортом, приходят уже после операции; полный `ConfigurationChangeDetector.detect` — O(число файлов) `stat` плюс перехеширование переписанного импортом, гонять его на каждое из тысяч запоздавших событий нельзя (см. «Два механизма подавления собственных файловых событий» выше) |
| Хеш-кэш: базовая линия и stat-мемо — два файла; неизменённые файлы не читаются, «изменено» решает хеш; проверка в расширении фоновая (`ChangeDetectionRunner`) | Полное перехеширование выгрузки на старте блокировало Extension Host на минуты; общий файл с CLI дал бы гонку за базовую линию импорта (см. «Хеш-кэш: базовая линия и stat-мемо» выше) |
| `-AllExtensions` у `/DumpCfg`/`/LoadCfg` не поддерживается ни в одном инструменте/команде | Платформа принимает флаг молча (exit 0) и выгружает ОСНОВНУЮ конфигурацию вместо расширений — она вообще не диагностирует неизвестные ключи, поэтому `exitCode` не может служить проверкой корректности вектора аргументов (см. «Паттерн: бинарный обмен CF/CFE» выше) |
| `/LoadCfg` не помечает конфигурацию проекта «изменённой» и не запускает `/UpdateDBCfg` | `/LoadCfg` меняет только основную конфигурацию, не базу; пометка «изменена» дала бы «обновить изменённые конфигурации» залить старые файлы проекта обратно в базу поверх только что загруженного CF (см. «Паттерн: бинарный обмен CF/CFE» выше) |
| Запись файла выгрузки — только через `infra/fs/AtomicFileWriter` (temp+rename), временный путь не `.xml`, `fsync` нет | Обрыв прямой записи оставляет обрезанный XML, а он делает нечитаемой всю конфигурацию; `.xml`-временный файл будил бы watcher; защита — от обрыва процесса, не от потери питания (см. «Атомарная запись файлов выгрузки» выше) |
| Допустимость дочернего тега (`META_TYPES.childTags`) и порядок сериализации (`CHILD_OBJECTS_ORDER`) — две разные оси, валидатор читает только первую | Проверка по оси порядка дала 16 945 ложных предупреждений на 3 660 эталонных файлах (стандартные реквизиты лежат не в `<ChildObjects>`); решение откачено (см. [xml-format-rulesets.md](./xml-format-rulesets.md#две-оси-допустимость-дочернего-тега-и-порядок-сериализации)) |
| Подключение ИБ агента держится между операциями, но освобождается перед любым пакетным 1cv8 и интерактивным Конфигуратором | Подключение не переживает закрытие SSH и блокирует базу для пакетного запуска; цикл «загрузить → обновить» не должен платить `connect-ib` каждый раз (см. «Удалённый сервер 1С» выше) |
| Синхронизация с агентом — модель M/P/B: дельта по `--get-changes`, архив при `FullDump`/неразборчивом списке/превышении порога | Платформа сообщает любое удаление и переименование как `FullDump`; полный архив — корректный, но медленный путь, дельта — оптимизация там, где список точный |
| Операции хранилища не публикуются как MCP-инструменты | Меняют общий для команды ресурс, требуют интерактивного комментария и пароля хранилища (см. «Удалённый сервер 1С» выше) |
